Bonsai SIMD sizing decision — 13 October 2026

Recommendation

Select a 128-lane signed add/subtract/skip dot engine as the analysis candidate,
with TWO engines at the existing 25 MHz, and a parameterized FOUR-engine option.
Do not implement eight engines now. Do not claim that two engines deliver a
measured 2x or 5x whole-model gain: the matched Bonsai INT8 baseline and activation
contract do not exist in the inspected evidence. On the unchanged core-fed
memory path, even two engines are unjustified for decode. The two-engine option
requires a dedicated streaming memory reader, local activation reuse and an
on-device group-scale/reduction path. If those are out of scope, select at most
one 64/128-wide diagnostic engine and do not promise significant model speedup.

This is a sizing decision and measurement plan, not authorization to implement
new RTL. Nothing was built, published, loaded or run on the shared F2 host.

The sensible target is 2x end-to-end first. A 5x goal is conditional on an
accelerable Bonsai time fraction above 80%, substantially better scheduling than
the current INT8 software path, and inclusion of conversion/scaling overhead.
Four engines are an expansion after bandwidth and phase measurements, not a
default procurement/area assumption. A same-throughput 4x64 alternative is worth
evaluating if 128-byte activation reads or reduction routing are the constraint.

Actual INT8 geometry and observed utilization

Pinned rvv_backend_define.svh: VLEN128 => TE16, COMPRATIO4/TE=1/4, four PE blocks,
16 physical 256-byte tile registers. Each block has (TE/2*COMPRATIO)*(TE/2)=2*8
dot cells. zvt_pe_mulbulk_int_lane.sv implements four active diagonal INT8
products per cell; disabled INT16 cross-products are not extra useful MACs.
64 cells * 4 = 256 INT8 MAC-equivalents/cycle, or 6.4 GMAC/s at25MHz (12.8 GOP/s
if multiply and add are counted separately). FP32 ceiling is64 products/cycle.
Four logical INT32 tiles are accumulator capacity, not four separate engines.
Tile storage totals4096bytes, implemented in registers/mux logic in this image.

An INT8 instruction describes up to M16,N16,K4 =1024 useful products, stripmined
over four row cycles. For M1,N16,K4, at most64 products are useful per command.
The RTL row counter can shorten small-M dispatch; therefore calling decode
utilization universally 1/16 is wrong. At a one-command/cycle arithmetic ideal,
M1 reaches64 products/cycle (25% of full peak), but DISPATCH2, four operand uops,
RAW hazards, loads, issue gaps and drains reduce this. A fixed issue schedule
can instead exhibit the 1/16 useful-work ratio, as the measured repeated case does.

Native workload and numerics

The executable fixture is Bonsai1.7B Q1_0, NOT a native ternary checkpoint:
128 binary signs plus an FP16 scale =18 bytes, sign bit1=+1,0=-1. The separate
32-byte ternary2 fixture has00=0,01=+1,10=-1,11=invalid and implicit scale1.
Do not convert the native checkpoint to this test encoding or invent zero sparsity.

Canonical manifest: 197 Q1 matrices, 113 FP32 vectors;242,357,184-byte image.
SHA256 ccd70c080f8758e1b4df58c2fdbdd6d13bb65571abbc56feb6942de1f8c07d99 was
rechecked against the entire local canonical payload in this analysis.
Exact matrix inventory (N,K,count):
  1024,2048,56; 2048,2048,56; 6144,2048,56; 2048,6144,28;
  151669,2048,1 tied embedding/output head.
K is divisible by128 throughout. Mask the151669-row head tail; never read past
tensor boundaries. Generic K tails require a new valid-lane contract, or reject
them under the existing native ABI. Zero-pad ACTIVATIONS only in a defined padded
test representation, not by reading beyond native packed groups.

One decode step's dense linears, including head once:1,719,904,256 products,
13,436,752 group dots and241,861,536 packed weight bytes. Embedding is a lookup,
not a second head matmul. INT8 expansion is1,719,904,256 bytes before scales,
which does not fit the current1GiB aperture. The fair INT8 baseline must unpack
bounded tiles from the same Q1 bytes, or account for explicit host streaming.
Both paths can read packed bytes from HBM; the ternary hardware does NOT get a
7.11x memory advantage over an INT8 path that already unpacks locally.

Fair operator contract: use the identical Xq int8 tensor on both paths;
INT8 path expands signs to signed{-1,+1}, accumulates each128-element group into
int32; candidate performs add/sub at width32/64/128. Widen before negating-128.
The group dot bound is+/-16384. Keep raw scale bits. Apply scales BEFORE summing
groups, in a frozen ascending-group FP32 rounding order; unequal scales prevent
one integer sum across K. Activation scale(s) must also be applied at the agreed
location and order. Quantizer range, rounding, saturation, granularity and
nonfinite handling must be frozen from actual model activations before a model
quality or throughput claim. A seeded int8 dot test is insufficient.

including signed extremes:1182 exact width-partition comparisons passed. This

FP32/BF16 activation inference cannot silently become int8 activation inference.
The existing Qwen path has Q8 weights with FP32 activations/KV and performs FP32

Bandwidth, overlap and diminishing returns

Existing core external AXI is128bits at25MHz: hard data-width bound0.4GB/s before
protocol/CDC stalls. HBM AXI300MHz is not the bandwidth seen by this client.
Existing ERG-103 store has16 logical slots but one physical read outstanding.
Duplicating clients behind that serial reader cannot supply the table above.
At read latency L core cycles its64-byte service roof is at most64*25e6/L B/s,
before issue bubbles. DOT128 rereads a full64B line (two for a crossing): for
dense aligned18B groups,25% cross a line, averaging80 physical bytes/group if
no line reuse. That is4.44x more traffic than the ideal18B/group roofline.

The only located device copy diagnostic is262144B in504465cycles:12.991MB/s of
copied payload (25.98MB/s counting reads+writes). Its zero-padding checksum is
weak; it is neither a peak-HBM qualification nor a read-only bandwidth ceiling.
The model sweeps13MB/s,50MB/s,0.2/0.4/0.9/1.6/1.8/3.6GB/s explicitly as
sensitivity inputs. No measured multi-engine payload bandwidth exists.

The dedicated adapter could use512bits at25MHz for at most1.6GB/s; that feeds
two Q1 engines at peak, not four at peak. More bandwidth needs independently
banked/wider ports or a faster reader plus asynchronous queues, with actual
interconnect and CDC validation. Do not change the25MHz core assumption.
For80% arithmetic occupancy, two/four Q1 engines need at least.72/1.44GB/s of
useful weights, plus activation/output traffic and margin. PTQ/PQ2 need more.
The saturation count is approximately ceil(B_eff/(f*W*bytes_per_weight)) for
decode; the last engine may be partly idle. Evaluate incremental latency saved,
not just whether an extra engine can be kept partly busy.

The max bound assumes independent DMA/compute/scaling stages overlap perfectly.
Without overlap use their SUM. For each tile, model startup+max(Tread,Tunpack,
Tdot,Tscale,Twrite)+drain; charge tails and repeated bytes. A descriptor queue
amortizes control; one host mailbox command per group would require13.4million
submissions per token and is not a credible execution schedule.

Scratchpad, ports and reduction requirements

Prefer K-parallel W128 over the old draft16x8 systolic mesh for this decision:
native128-element groups align exactly; decode uses all lanes with no mesh fill
or folded-mode routing assumption. A seven-level combinational reduction should
not be assumed to close timing; pipeline it and track row/group/epoch metadata.
Distribute independent output rows across engines, broadcast one128-byte Xq
group, and keep each output's group order. Using multiple engines on the SAME
row needs an additional ordered merge and should not be the initial mapping.

Proposed storage BUDGET (not a synthesized BRAM count) for shared token tile8,
output tile16, maxK6144: double activation buffers need96KiB; reserve128KiB for
alignment/banking. Q1 double full-K weight panels need27648B; reserve32KiB.
Reserve8KiB for result queues, accumulators, descriptors and line assembly:
about168KiB added storage, physically banked. This exceeds32KiB DTCM, whose
firmware/stack already consume capacity. It must be accelerator-local memory.
PTQ/PQ2 need larger weight buffers or smaller tiles; rederive from selected model.

Activation read is128B/cycle shared across engines at the same group/token;
eight16B banks (or equivalent wide banking) with a separate write bank suffice
conceptually. E weight banks must collectively deliver18E B/cycle for Q1 plus
format decoding. Banking groups/panels on ingest is required because row-major
groups at equal K are strided in HBM; issue contiguous row bursts and transpose
only the bounded panel. Ping-pong banks avoid read/write conflicts. Replicated
activation memories or fanout pipeline registers may be needed for routing.
Scalar DTCM loads cannot provide these ports. Capacity alone proves nothing.

At two engines,50million group results/s require at least two scaled reductions
per core cycle to retain peak compute. Software FP32 scaling/draining through
one scalar unit cannot be assumed to keep up. Batch/vectorize independent rows,
or fuse an explicitly specified scale/reduction pipeline. Keep enough independent
row accumulators to hide pipeline recurrence latency; retain ascending group
order and avoid FMA/reassociation unless the numerical contract permits it.
Returning6bytes/group to HBM/core adds80.62MB per decode step; keeping final
row accumulators local and writing only final outputs is preferable.

End-to-end target and break-even decision

Let p be the measured fraction of matched baseline time replaced by the entire
new kernel (including old unpack/scale work), s its speedup, and d added time as
a fraction of original total. End-to-end speedup=1/(1-p+p/s+d).
Break-even requires d < p*(1-1/s). If p<=.5, no finite kernel makes2x with d>=0;
if p<=.8, no finite kernel makes5x. Ignoring new overhead:
 p             s needed for2x       s needed for5x
 .60                  6                  impossible
 .70                  3.5                impossible
 .80                  2.667              infinite limit only
 .90                  2.25               9
 .95                  2.111              6.333

Illustrative decision gates, NOT forecasts: with75% total engine efficiency,
two128 engines give4.8GMAC/s. For p=.8 and target2x, the matched replaced kernel
must currently achieve <=1.8GMAC/s, with negligible added overhead. Four engines
at75% give9.6GMAC/s, lifting that threshold to3.6GMAC/s. For p=.9 and target5x,
the corresponding thresholds are.533/1.067GMAC/s. Include real bandwidth and
scale limits before applying these thresholds. The observed small INT8 loops
cannot substitute for a streaming Bonsai operator measurement.

Against a well-fed full INT8 prefill ceiling6.4GMAC/s, two128 engines have NO
arithmetic peak advantage; four give2x, eight4x. Even4x kernel gain at p=.9 is
only3.08x end-to-end. A5x claim must demonstrate removal of current overhead or
broader fused work, not merely replication. Against a decode bound1.6GMAC/s,
two engines have4x theoretical arithmetic headroom, still conditional on feeding.

Qwen evidence, explicitly separate: optimized TTFT186.3877s, total560.2247s,
decode.00534993tokens/s,455808 bitexact logits. Device phases251.766s conversion,
195.796s matrix,87.023s combine,25.635s other. Making ONLY its matrix phase free
would cap gain at1.537x. These numbers motivate measuring/fusing conversion and
reduction; they neither estimate Bonsai's p nor establish its activation precision.

Resource-normalized versus added-resource comparison

Two128 engines have256 simple signed product-equivalent lanes, equal in count
to Coral's256 INT8 products/cycle. This is an operation-count normalization,
NOT equal FPGA area/power. Add/sub/skip can avoid weight multipliers but needs
unpackers, reduction trees, scales, FIFOs, banked SRAM and interconnect. Four and
eight engines add2x/4x product slots compared with Coral and must be labeled as
added-resource designs if Coral remains present. Also compare software-only
unpack/scale improvements and a banked tile-store improvement as competing uses
of area/engineering effort; no claimed savings before synthesis.

Practical integration sequence after decision

Preserve DOT128 v1 as the diagnostic contract. First close ERG-103's own simulator,
actual-weight sealed FPGA, driver/mailbox and review/merge gates. Alex image reuse
requires a separately reviewed mapping, not renaming the Qwen pass.
Then version a tile/descriptor ABI and memory client, preserving tags, epochs,
backpressure, sealing, fault/drain/reset semantics. Add streaming burst reads,
line reuse and scratchpad ownership; seal ALL paths that could write weights,
including core/DMA/host. Keep activation/KV regions writable and disjoint.
Expose full-operator completion plus byte/stall/compute/scale counters. Verify
CPU reference -> simulator -> bounded physical native operator -> layer -> model,
with identical numerical contracts. Expand two to four only when measured p,
bandwidth and scaling meet the target equations and routing fits. Leave eight
out until a new measured bottleneck analysis supports it. Parent coordinates any
future host window and Alex image process; this deliverable performs no such work.
